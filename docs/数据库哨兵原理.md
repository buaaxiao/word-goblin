# 数据库增量哨兵原理说明

> 适用模块：`acctMgnt/cmpak_tools/JavaWorkSpace/XWordGoblin`
> 涉及文件：[js/storage.js](../js/storage.js)、[js/db.js](../js/db.js)

---

## 一、要解决什么问题

单词精灵的用户数据（章节 / 单词 / 历史）存在浏览器 **IndexedDB** 里。IndexedDB 有两个关键特性：

1. **所有 API 都是异步的**（回调 / Promise），`saveData()` 要串行发起很多次事务：

   ```
   dbGetAllChapters → dbPutChapter × N → dbDeleteChapter × M
   dbGetAllWords    → dbPutWord    × N → dbDeleteWord    × M
   dbGetAllHistory  → dbPutHistory × N → dbDeleteHistory × M
   ```

2. **没有跨事务的全量原子性**。每次 `dbPutXxx` 都是一个独立事务，只有单条记录是原子的。

于是就会出现「**写了一半**」的中间状态：

| 场景 | 结果 |
| --- | --- |
| 写章节成功 → 写单词时事务中止 | 内存里单词已改，库里的单词还是旧的 |
| 写单词时抛 `QuotaExceededError` | 部分记录更新、部分没更新 |
| 循环中任意一次 `dbPutXxx` reject | 后续记录全部没写 |

内存中的 `data.chapters` 已经是最新状态，可一旦刷新页面，内存丢失，IndexedDB 里只剩「半新半旧」的数据 → **用户看到自己的修改凭空消失**。

**哨兵（sentinel）就是为这个场景准备的一份「未完成写入的补丁包」。**

---

## 二、哨兵是什么

哨兵是一条写在 **sessionStorage** 里的增量记录，键名：

```js
// js/storage.js
const PENDING_KEY = "wordDictation.pending.v1";
```

它只记录「**本次写库过程中，还没能确认全部落库的那些变更**」，结构如下：

```js
{
  chapters: { "ch_xxx": { id, name, selected, dictLang, order } },  // 需要写入/更新的章节
  words:    { "w_xxx":  { id, chapterId, text, meaning, ... } },    // 需要写入/更新的单词
  history:  { "h_xxx":  { id, date, chapters, total, ... } },       // 需要写入/更新的历史

  deleted: {                                                       // 需要删除的主键
    chapters: ["ch_yyy", ...],
    words:    ["w_yyy",  ...],
    history:  ["h_yyy",  ...]
  },

  ts: 1730000000000                                                 // 记录时间戳（诊断用）
}
```

要点：

- **不是全量数据**，只存「变化的那部分」，所以体积很小。
- 键是主键（`ch_` / `w_` / `h_` 前缀的 uid），value 是完整记录对象 → 回放时可以直接 `put`。
- 删除用 `deleted` 数组表达，回放时 `delete`。

## 三、写入侧：哨兵在哪一刻产生

`saveData()` 的执行流程（[js/storage.js](../js/storage.js)）：

```
saveData()
  │
  ├─ 1. 收集增量 diff → changed { chapters, words, history, deleted }
  │
  ├─ 2. 逐条写 IndexedDB（章节 → 单词 → 历史）
  │       每写一条，就记进 changed.*，便于失败时回放
  │
  ├─ 3. 全部成功：
  │        sessionStorage.removeItem(PENDING_KEY)   ← 清掉上一次可能遗留的哨兵
  │        console.log("[saveData] 增量写库完成：更新 x章/y词/z历史 …")
  │
  └─ 4. 任意一步抛异常（catch）：
           prev   = readPending()                   ← 读旧哨兵（可能没有）
           merged = mergePending(prev, changed)     ← 与本次变更合并
           sessionStorage.setItem(PENDING_KEY, JSON.stringify(merged))
           console.warn("[saveData] 已写入增量哨兵，下次启动会恢复")
```

也就是说：**哨兵只在「写库失败」的瞬间被写入**，成功路径上不会留下任何残留。

### 3.1 合并规则 `mergePending`

失败可能连续发生多次（用户改一次失败一次），所以新旧哨兵要合并，规则是「**后写覆盖先写**」：

```js
// 1) 新增/更新：对象浅合并，后一次覆盖前一次
chapters: Object.assign({}, prev.chapters, next.chapters)
words:    Object.assign({}, prev.words,    next.words)
history:  Object.assign({}, prev.history,  next.history)

// 2) 删除：并集去重
deleted.chapters = uniqConcat(prev.deleted.chapters, next.deleted.chapters)

// 3) 冲突消解：既在 upsert 又在 deleted 里的主键 → 以 upsert 为准（写赢）
out.deleted.chapters = out.deleted.chapters.filter(id => !out.chapters[id]);
```

第 3 条很关键：同一个 uid 先被删、后又被写回（例如撤销删除、或云端合并重新插入），
如果按「删除优先」，回放时会被错误地删掉；按「写优先」，最终状态与内存一致。

## 四、读取侧：哨兵在哪一刻被消费

`loadData()` 的第一步就是检查哨兵（[js/storage.js](../js/storage.js)）：

```
loadData()
  │
  ├─ 0. pending = sessionStorage.getItem(PENDING_KEY)
  │      有内容 → console.warn("[loadData] 检测到未提交的增量哨兵，回写 IDB：…")
  │              applyPendingToIDB(pending)          ← 回放补丁
  │              sessionStorage.removeItem(PENDING_KEY)   ← 成功才清除
  │              console.log("[loadData] 增量哨兵已回写并清除")
  │
  ├─ 1. migrateFromLocalStorage()   ← 旧数据一次性迁移
  ├─ 2. dbGetAllChapters / Words / History
  ├─ 3. 组装内存 data.chapters / data.history
  └─ 4. console.log("[loadData] 从本地 IDB 载入完成：章节 x 个 · 单词 y 个 · 历史 z 条，耗时 nms")
```

### 4.1 回放顺序 `applyPendingToIDB`

```js
// ① 先删除
deleted.words    → dbDeleteWord(id)
deleted.chapters → dbDeleteChapter(id) + 级联 dbDeleteWord(该章节下所有单词)
deleted.history  → dbDeleteHistory(id)

// ② 再写入 / 更新
pending.chapters → dbPutChapter(rec)
pending.words    → dbPutWord(rec)
pending.history  → dbPutHistory(rec)
```

**先删后写**：这样即使同一主键同时出现在 `deleted` 和 upsert 中（理论上已被 `mergePending` 过滤），
最终结果也一定是 upsert 的记录存在；同时删除章节时先删章节再删其单词，不会误删刚写回的单词。

每条记录的操作都包在独立的 `try/catch` 里，单条失败不影响其它记录。

### 4.2 幂等性

- 回放成功 → `removeItem` → 下次启动不会重复回放。
- 回放过程中抛错 → 不 `removeItem` → 下次启动再试一次。
- 回放本身是「按主键 put/delete」，重复执行结果一致（幂等），因此重试是安全的。

## 五、整体时序

```
录入一次操作（如勾选章节）
        │
        ▼
   saveData()  ──创建 diff──►  changed
        │
        ├── 逐条写 IndexedDB ──► 成功 ──► 清哨兵 ──► 结束
        │
        └── 抛异常 ──► mergePending(旧哨兵, changed)
                        │
                        ▼
              sessionStorage[wordDictation.pending.v1] = 补丁
                        │
        ┌───────────────┘
        │  用户刷新 / 重开页面
        ▼
   loadData()
        │
        ├── 读哨兵 ──有──► applyPendingToIDB（先删后写）──► 清哨兵
        │
        └── 读 IndexedDB ──► 组装内存 data ──► 渲染
```

## 六、设计决策与边界

### 6.1 为什么用 sessionStorage 而不是 localStorage

| 维度 | sessionStorage（当前方案） | localStorage |
| --- | --- | --- |
| 生命周期 | 标签页关闭即失效 | 永久 |
| 多标签页 | 各标签页独立，互不干扰 | 共享，互相覆盖 |
| 语义 | 「本次未完成事务」的临时快照 | 长期数据 |

哨兵描述的是「**这个标签页上一次没能写完的东西**」，天然属于会话级；
放 localStorage 反而会带来跨标签页覆盖与「过期补丁永远赖着不走」的问题。

### 6.2 与「删除黑名单」的区别

两者常常被混淆，但职责完全不同：

| | 增量哨兵 | 删除黑名单 |
| --- | --- | --- |
| 键 | `wordDictation.pending.v1`（sessionStorage） | `wordGoblin.deletedUids.v1`（localStorage） |
| 目的 | **崩溃恢复**：把没写完的改动补回去 | **防复活**：云端同步时不重新拉回用户删掉的章节/单词 |
| 生命周期 | 消费一次即清 | 长期保留，直到同名 uid 重新出现 |
| 内容 | 需要写入/删除的完整记录 | 仅 uid 列表 |

### 6.3 已知边界

1. **页面被强杀（浏览器崩溃、任务管理器结束进程、写入过程中立刻刷新）时 catch 不会执行**，
   此时不会产生哨兵，那一批改动无法恢复。哨兵覆盖的是「异常可被捕获」的失败
   （事务中止、`QuotaExceededError`、代码抛错等）。
2. `applyPendingToIDB` 内部逐条 `try/catch` 会吞掉单条错误，因此**即使有个别记录回放失败，
   也会执行 `removeItem`**，该条改动会丢失。若需更严格，可把失败计数返回并在 > 0 时保留哨兵。
3. sessionStorage 容量约 5 MB，哨兵是增量数据，正常远小于该上限；但如果一次性导入超大词库且写库失败，
   写入哨兵本身也可能抛错（代码里已在 `catch (err)` 中降级为日志）。
4. 哨兵只服务当前标签页，关闭该标签页即彻底丢失。

## 七、如何验证

### 7.1 人工构造哨兵

1. 打开页面，DevTools → Console：

   ```js
   // 假装有一条没写进去的章节改名
   sessionStorage.setItem(
     "wordDictation.pending.v1",
     JSON.stringify({
       chapters: {
         ch_demo: { id: "ch_demo", name: "哨兵测试章节", selected: true, dictLang: 1, order: 0 },
       },
       words: {},
       history: {},
       deleted: { chapters: [], words: [], history: [] },
       ts: Date.now(),
     }),
   );
   ```

2. 刷新页面，Console 应依次出现（对象参数在 DevTools 里可展开，导出到 `.log` 时为 JSON）：

   ```
   [loadData] 检测到未提交的增量哨兵，回写 IDB： { upsert: "1章/0词/0历史", deleted: "0章/0词/0历史" }
   [storage] 增量哨兵已应用到 IDB： { upsert: "1章/0词/0历史", deleted: "0章/0词/0历史" }
   [loadData] 增量哨兵已回写并清除
   [loadData] 从本地 IDB 载入完成：章节 N 个 · 单词 M 个 · 历史 K 条，耗时 Tms
   ```

3. 章节列表里应出现「哨兵测试章节」，并且 `sessionStorage.getItem("wordDictation.pending.v1")` 变为 `null`。

### 7.2 观察真实写入

DevTools → Application → Storage 面板：

- `Session Storage` → 观察 `wordDictation.pending.v1` 何时出现 / 消失。
- `IndexedDB` → `wordGoblinLocal` → `chapters / words / history` 核对数据是否落库。
- `IndexedDB` → `wordGoblinLocal` → `logs` 查看运行日志（由 [js/logger.js](../js/logger.js) 落盘，
  级别控制来自 vendored 的 [lib/loglevel.min.js](../lib/loglevel.min.js)），
  设置弹窗「系统设置 → 运行日志 → 导出日志」可导出为 `.log` 文件；
  「系统设置 → 日志级别」可调**写入日志文件**的详细程度（浏览器控制台始终完整打印）。

## 八、相关日志速查

| 日志关键字 | 含义 |
| --- | --- |
| `[saveData] 增量写库完成：更新 … 删除 …` | 本次写库的增量规模与耗时 |
| `[saveData] 无变化，未写库` | diff 为空，未触发任何事务 |
| `[saveData] 已写入增量哨兵，下次启动会恢复` | 写库失败，已生成恢复补丁 |
| `[loadData] 检测到未提交的增量哨兵，回写 IDB` | 启动时发现补丁并开始回放 |
| `[storage] 增量哨兵已应用到 IDB` | 补丁回放完成（含条数） |
| `[loadData] 增量哨兵已回写并清除` | 补丁消费完毕 |
| `[db] 事务失败 / 事务中止：<store> / <mode>` | 具体是哪个对象仓库写失败 |

> 注：`logs` 仓库自身的写失败不会打印，避免「日志写失败 → 再记一条日志」的递归。
